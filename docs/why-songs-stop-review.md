Evidence: (scratch)/uptime.log
- **Trigger:** The controller is on a different access point from every earlier reading. Today it is on BSSID E0:63:DA:71:F4:EF, channel 6, at -84 to -95 dBm. From Oct 27 to Oct 30 it was on E0:63:DA:84:03:1E, channels 1 and 11, at -52 to -66 dBm. In uptime.log up to 12:58, 43 of 115 GETs got no answer in 4 s (37%), up to 5 in a row (about 95 s), while uptime kept rising, so these are link outages and not restarts. Only the IP path crosses this link; a phone on the helmet's own AP does not, which fits the owner's 'over IP'. The last good reading on the old AP was Fri 18:46 PDT, so this only explains an incident after that time. Ask when it happened.
- **Path:** 1. Frames stop arriving. After realtimeTimeoutMs (2500 ms, cfg if.live.timeout 25), udp.cpp:485 calls exitRealtime, and show() blends the empty frozen segments (FX_fcn.cpp:1695-1701), so the helmet goes dark.
2a. If the link stalls for 5 s, AsyncTCP's default 5 s ack timeout (AsyncTCP.cpp:1086-1096) closes the socket (AsyncWebSocket.cpp:510-513). The browser sees the close when the link returns.
2b. If the STA association drops, network.cpp:447 clears interfacesInited and wled.cpp:947-951 runs initConnection: WiFi.disconnect(true) and WiFi.mode(NULL) (wled.cpp:700, 713), then another attempt every 18 s until it joins. The netif going away aborts the sockets on the controller (lwIP behaviour, not measured), and the RST cannot reach the browser.
3. In the browser ws.readyState stays 1. busy() waits 1 s plus 1.5 s, sends 3 more frames, and repeats forever; it never closes the socket. reopen() only runs when link.ws is null (wire.js:938). watchLink says nothing while readyState is 1 (ui.js:186-193). I simulated this against a copy of wire.js: after 20 s it was the same socket, 1 open, 0 relayouts, 24 frames and about 100 kB queued.
4. In case 2b the page learns only at the next TCP retransmit, which draws an RST. Retransmit gaps double, so after a long outage the wait can be about as long again (general TCP behaviour, not measured). A reload opens a fresh connection and works at once.
- **Symptom:** LIGHTS go dark about 2.5 s after the last frame. The page shows no warning, and its preview and clock crawl at 3 frames per 2.5 s. MUSIC keeps playing: the song is a blob from IndexedDB with no network dependency. The lights come back without a reload once the link and socket recover, but a reload is the quick cure in case 2b. A reload is also what stops the song, so 'it stopped, I had to reload' fits this path. That last link is an inference.
- **Fix:** Today: ask whether the helmet moved. While idle, GET /json/net to list each AP's BSSID and RSSI. It starts a scan that takes the radio off channel, so never do it during a stream. WLED only picks the strongest AP at join time (wled.cpp:510) and never roams, so power-cycle it near the strong AP or pin nw.ins[0].bssid. If the show location is weak, use the helmet's own AP instead.
Code, wire.js: record `this._heard = performance.now()` in onopen, in onmessage and in begin(). At the top of the open-socket branch of busy(): `if (now - this._heard > 4000) { const d = this.ws; this.ws = null; this.unacked = []; this.owed = 0; this.dirty(); try { d.close(); } catch (e) {} return this.inflight >= this.maxInflight; }`. The existing reopen, _relayout and the 'lost the helmet' message then take over. Keyframes every 1 s guarantee a pong, so 4 s of silence is real. Also raise openSocket(1500) in reopen to about 3000, because a handshake on this link can exceed 1.5 s.

## [medium] The audio context can leave 'running' with nothing watching it, silencing an element that still reports playing. A dead context is the one path in the code that truly needs a reload.

- **Where:** remote/offline/audio.js:167 (_ctx resumes only on 'suspended', so it misses Safari's 'interrupted'); audio.js:247 and 271-279 (the sound is routed only through the context); audio.js:257 (unlock); ui.js:1806 (resume on visibility return only); ui.js:1455-1459 (showpp resumes neither the context nor anything else). There is no onstatechange or ctx error handler anywhere.
- **Trigger:** Desktop: output device failure or removal, an audio service restart, or a Bluetooth or HDMI output vanishing. iOS: any interruption, screen lock or app switch. Android: rare.
- **Path:** ctx leaves 'running' while the page is in front -> the element is wired only through createMediaElementSource, so its output goes nowhere audible -> el.paused stays false, so showPP says 'pause' and the page looks healthy. From memory of Chromium, not measured: nothing pulls the element while the context is stopped, so currentTime stalls and the lights freeze at ui.js:261. On Safari the clock may run on silently, so the lights carry on with no sound. Recovery exists only on a visibility flip, or a tap on start, Play Music, next or prev, which call unlock. On iOS the resume from visibilitychange has no gesture behind it and may not take; at that point showgo means stop, and showpp does not resume the context, so stop then start, from 0:00, is the only remedy. If the context is actually dead, an.ctx is kept for the life of the page and the single element can only ever be wired to it, so every later song is silent until a reload. That matches 'I just had to reload'. No evidence for this on this Mac: the built-in speaker session ran unbroken from 19:00:12 to 20:45:34 across the 19:02:11 stop. To settle it, watch the statechange logging suggested in the media-key finding, or on an iPhone lock the screen mid-song and come back.
- **Symptom:** MUSIC goes silent with no message. LIGHTS freeze on desktop Chrome and may keep running on Safari. - **Trigger:** The controller restarts, the socket reconnects, and the layout POST times out, as it can at this signal. Simulated: socket up, 0 relayouts, 0 retries in the next 30 s.
- **Path:** The catch swallows the failure. The comment says the next reconnect tries again, but the socket is up, so there is no next reconnect. Binary frames still land, because realtime writes pixels without the segments and realtimeLock lights a strip that booted off. _keepOn then posts on:true without any frozen segments.
- **Symptom:** During steady streaming the LIGHTS look normal. In any frame gap of 2.5 s or more, the helmet shows WLED's own boot state (its default solid colour or the standby preset, unfrozen) instead of going dark, until the next stop and start. MUSIC unaffected. No reload needed.
- **Fix:** In the catch set this._needLayout = true, clear it on success, and in _keepOn (every 5 s) call this._relayout() when it is set.

## [low] OPEN. A truly lost pong pauses frames for almost exactly the realtime timeout

- **Where:** remote/offline/wire.js:600-601 (1000 + 1500 ms at depth above 1), wire.js:945-955 (busy), udp.cpp:485 (realtime exit at the 2.5 s timeout in the helmet's config).
- **Trigger:** Pongs that never arrive, such as the firmware dropping one. Late pongs do not cause this, because they end the wait early through _pong.
- **Path:** Simulated: pongs missing for 100 ms gave a 2430 ms gap between frames, against a 2500 ms realtime timeout. That leaves a 70 ms margin before any network jitter.
- **Symptom:** LIGHTS freeze about 2.4 s and may blink dark as realtime exits, then recover alone. MUSIC unaffected. No reload.
- **Fix:** On the binary path use the short quiet period: this.owedQuiet = (d > 1 && !this.binary) ? OWED_QUIET_MS : OWED_QUIET_1_MS. hello() already sets this.binary before calling _setDepth. The drift that the long wait protects against comes from JSON backlog, which the binary path does not have.

## [low] OPEN, NEW WITH THE WORKER CLOCK. A worker error while hidden leaves a running loop with no timer

- **Where:** remote/offline/ui.js:151 (clock.onerror), ui.js:156-161 (later), ui.js:1795 (the visibility handler requires clock to be non-null).
- **Trigger:** The worker errors, or a posted wake-up is lost, while the page is hidden. Unlikely, since it is a one-line script.
- **Path:** later() has already posted to the worker and scheduled nothing else. onerror sets clock=null and schedules nothing. When the page becomes visible, ui.js:1795 skips because clock is null, and it also skips whenever parked is true. state.running stays true.
- **Symptom:** LIGHTS stop, MUSIC keeps playing, and the button says 'stop' with the numbers frozen. Stop then start recovers, because start calls tick. No reload needed.
- **Fix:** clock.onerror = () => { clock = null; if (state.running) later(50); }; and at ui.js:1795 use if (state.running) later(parked ? 50 : 0);

'Harder Better Faster Stronger' and 'Some Chords' had no scenes yet in that build, so re-run once the songs are final: node (scratch)/linkreview/sweep_fast.js (run it from that folder). If it ever trips, stop() leaves the music playing and stopNote unset, so a single song has no auto-restart; a playlist restarts at its next track.
- Silent fallback from scenes to a dark helmet: not possible. ShowPlayer.frame catches a scenes failure and uses the cue list, and _shows() in mau5offline.py skips any show without cues, so a cue list always exists.

- link.busy parking forever: no. step re-checks every 50 ms, owed is forgotten after the quiet period, and HTTP inflight is bounded by POST_TIMEOUT_MS through AbortController.
- Socket stuck in CONNECTING: no. The giveUp timer at wire.js:559 closes it and resolves false. The 'another is live' return at wire.js:565 would leave the promise unresolved, but it is unreachable because openSocket shares one connection attempt at a time.
- Reconnect back-off giving up: never. reopen retries every 3 s for as long as streaming is true. _opening cannot stick, because both promise outcomes clear it.
- _keepOn stuck on _arming: no. Every request goes through _req with a 5 s abort, and finally clears the flag. Another client posting on:false is revived within 5 s plus one request.
- Frames cannot throw: ws is only assigned once open, and send on a CLOSING or CLOSED socket drops silently. Exceptions from a pong are inside tick's try. No path through step leaves without calling later().
- start() stuck forever: the only unbounded await is held at ui.js:672, and stop's pause() rejects a pending video play. hello and begin are bounded by request limits, about 32 s worst case. No start that fails leaves starting set, so the button is not stuck, though it says 'stop' during that wait.
- Controller restart on the binary path: frames do not need the segment layout. setRealtimePixel writes the frame buffer and FX_fcn.cpp:1695 skips blending during realtime. realtimeLock lights a strip that booted off (udp.cpp:426-428). The page recovers on its own once a socket returns.
- Analysis fetch hanging: pickShow now races it against 1.5 s (ui.js:1017), so it cannot hold up a song. A fetch that truly hangs stays pending in the drives map, so that song runs on live analysis until reload. That is a quality issue, not a stop.
- Guard NaN and thermal: sane() and the finite checks hold, and the thermal limit dims but never goes dark. Nothing in the repo sends lor, which is the one state that would make WLED ignore frames while the page thinks it is running.
- Restart cause: today's two observed restarts (about 12:20:40 and 12:24:23) happened with ws=0 and live=False, so they were not caused by streaming. The official build does not report a reset reason: resetReason0 and resetReason1 in json.cpp:841-843 are inside WLED_DEBUG, so /json/info cannot say why. mau5offline.py's deploy_drives docstring records that uploads have rebooted the controller mid-upload, which is worth checking against what other sessions ran.
